# 03: 模型归属路由 + `/v1/messages` 完整行为

**做什么：** 真实配置驱动 `/v1/messages` 的全部行为：按请求体中的 `model` 精确匹配启用的 Provider 转发；未命中、未识别路径、上游失败等所有错误路径符合 spec 定义的形态。完成后 `/v1/messages`（非流式部分）达到最终行为。

**阻塞于：** 02（ConfigStore 快照可用）。

**状态：** 完成

## 上下文

- **相关用户故事**：spec 3（按 model 匹配路由）、4（未命中 404）、11（上游错误原样透传）、12（网关连不上上游 502）、13（headers 透传 + 鉴权头替换）、23（未识别路径 404）。
- **设计决策**（自 design「3 接口设计」摘录）：
  - **路由**：`model` 与各启用 Provider 的 `models` 精确匹配（无通配、无兜底、无顺序仲裁——重复模型在保存时已被任务 02 拒绝）。请求入口取 ConfigStore 当下快照并全程使用。
  - **通用约定**：路径前缀 `/v1`；查询参数一律忽略；网关不校验客户端凭据；客户端 headers 原样透传，仅 `x-api-key`/`authorization` 替换为命中 Provider 的 apiKey；请求体与响应体不改写（含 `model` 名）。
  - **错误体**：Anthropic error 格式 `{"type":"error","error":{"type":"...","message":"..."}}`。
  - **错误路径**：
    | 场景 | 返回 |
    |---|---|
    | `model` 未被任何启用 Provider 声明 | 404 `model_not_found` |
    | 未识别路径（此任务中除 `/v1/messages` 外的一切） | 404 `not_found_error` |
    | 网关连不上上游（首字节前） | 502 `api_error` |
    | 上游返回任何 HTTP 错误（含 4xx） | 原样透传，状态码、headers、错误体不改 |
  - 不做故障转移、不重试（spec 范围外）。
- **术语**：模型归属路由的定义见根目录 CONTEXT.md。
- **seam 约定**：复用任务 01 立起的 **HTTP 端到端 seam**（进程内假上游 + 网关 + 真 HTTP 客户端）——本任务全部验收用例在该 seam 上断言；路由匹配本身可另加纯逻辑单元测试。

## 验收标准

- [x] 端到端：配置两个启用 provider（各声明不同模型），请求分别路由到正确上游；请求体（含 `model`）原样到达上游
- [x] 端到端：请求的模型只被**禁用**的 provider 声明 → 404 `model_not_found`（Anthropic 错误体）
- [x] 端到端：上游返回 401/429/500 → 状态码与错误体原样到达客户端
- [x] 端到端：上游不可达（如无监听的端口）→ 502 `api_error` Anthropic 错误体
- [x] 端到端：未识别路径（如 `/v1/other`）→ 404 `not_found_error`
- [x] 端到端：运行中经 ConfigStore 换快照（启/停 provider、改模型列表），后续请求立即按新配置路由，在途请求不受影响
- [x] 路由匹配的纯逻辑单元测试：命中、未命中、跨启用状态
